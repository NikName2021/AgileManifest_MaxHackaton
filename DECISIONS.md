# Решения по контракту и осознанно отложенное — пояснение для frontend

Этот документ — ответ на раздел 3 и известные ограничения `BACKEND_HANDOFF.md`: что именно решено,
что сознательно не сделано в рамках хакатона и почему. Не технический долг «забыли», а взвешенный
выбор с учётом сроков и того, что реально проверяется в демо/жюри.

## 1. Сессия — `Authorization: Bearer <token>`, не HttpOnly cookie

**Что сделано.** `POST /api/auth/max` принимает `initData` мини-приложения, проверяет HMAC-подпись
и выдаёт токен, который клиент кладёт в заголовок `Authorization: Bearer <token>` на каждый запрос.
Токен подписан HMAC на сервере, живёт 30 дней, содержимое — `userId.expiresAt.signature`.

**Почему не cookie.**
- Mini-app в MAX открывается во встроенном WebView, где нет гарантии, что произвольный домен API
  и домен, с которого отдаётся фронтенд mini-app, совпадают — а `HttpOnly`-cookie без явной настройки
  `SameSite=None; Secure` и без общего домена между API и mini-app просто не долетит до бэкенда.
  Bearer-токен в заголовке этой проблемы не имеет вообще — он не зависит от домена/схемы хранения
  куки в конкретном WebView.
- `initData` — это не логин/пароль пользователя, а одноразовый подписанный набор параметров, который
  MAX сам передаёт при каждом открытии mini-app. Из него логично сразу получить токен и хранить его
  на стороне клиента (localStorage/sessionStorage) — cookie не даёт тут никакого дополнительного
  уровня защиты, а только добавляет ограничения по домену/CORS, которые пришлось бы решать отдельно.
- Готовый адаптер фронтенда, о котором пишет хендофф, был написан ДО того, как этот эндпоинт вообще
  появился — это не наше протестированное решение, которое мы меняем на ходу, а первое и единственное
  решение по факту первой реализации auth. Менять его на cookie сейчас — это дополнительная работа
  (CORS с credentials, самдомен/прокси) без выигрыша в безопасности для этого кейса.

**Что это значит для фронта.** Токен, полученный из `POST /api/auth/max`, кладётся в заголовок
`Authorization: Bearer <token>` для каждого следующего запроса. Хранить его нужно на стороне
клиента (например `localStorage` внутри WebView mini-app) — это стандартная практика для
Telegram/MAX-подобных mini-apps, не отдельное решение "по бедности".

## 2. Роль не хранится отдельным полем — доступ по владению записью

**Что сделано.** В таблице `users` нет столбца `role`. Любой авторизованный пользователь может и
создать/опубликовать вакансию (то есть выступить работодателем), и откликнуться на чужую (выступить
кандидатом) — в том числе один и тот же человек в течение одной сессии. Доступ к конкретной записи
определяется владением: `vacancy.employerUserId`, `application.candidateUserId`.

**Почему не сделали роль.**
- По кейсу и сценарию хакатона нет требования разделять роли на уровне аккаунта — по сути любой
  пользователь MAX потенциально и работодатель (для своего бизнеса), и кандидат (для чужого). Жёсткое
  разделение ролей добавило бы шаг регистрации/выбора роли, которого нет в сценарии ни в ТЗ, ни
  в макетах — это лишний UX-барьер без функциональной необходимости для MVP.
- Owner-based модель проще и надёжнее: 403 выдаётся по факту владения записью, а не по флагу в
  профиле, который надо было бы отдельно поддерживать в актуальном состоянии (что происходит, если
  пользователь и то, и другое одновременно — как в нашем сценарии?).
- Если для финала понадобится строгое разделение (например отдельный «кабинет работодателя» с
  верификацией бизнеса) — это отдельная фича поверх текущей модели, а не переделка: `role`
  добавляется как новое поле, все текущие owner-проверки остаются рабочими как есть.

**Что это значит для фронта.** Не нужно спрашивать/хранить роль пользователя на клиенте для решения
"что показывать" — эндпоинты сами возвращают только то, что доступно вызывающему (`GET /api/vacancies`
— только свои вакансии, `GET /api/vacancies/:id/applications` — 403 на чужую). UI может предлагать
и раздел «Мои вакансии», и «Мои отклики» одному и тому же пользователю одновременно.

## 3. Нет полноценной очереди/retry для исходящих сообщений MAX (лимит на чат теперь соблюдается)

**Уточнение.** Ранее в этом документе было написано, что официальный лимит частоты отправки
сообщений в один чат нигде не опубликован — это было неточно, фронтенд справедливо указал на
[документацию MAX](https://dev.max.ru/docs-api/methods/POST/messages): лимит **2 сообщения в
секунду на один чат** задокументирован. Спасибо за уточнение — раз число известно, дёшево его
и соблюсти: теперь `max/client.ts` выдерживает минимум 550 мс между отправками в один и тот же
`chat_id` (небольшой запас сверх 500 мс). Между разными чатами сериализации нет — лимит именно
"на чат", не глобальный.

**Что по-прежнему не сделано и почему.** Полноценная очередь с персистентностью, retry с backoff
при временном сбое MAX и разбором "сообщение реально не ушло" vs "ушло, но ответ потерялся" — это
отдельный компонент сопоставимого объёма с уже сделанной частью backend. При объёме сообщений
одного MVP-бота на демо (один-два тестовых пользователя, штучные вакансии и отклики) риск не
успеть за 2 сообщения в секунду и без явного троттлинга был околонулевым — сам троттлинг теперь
закрывает и эту вероятность впрямую. Delivery retry поверх этого — уже вопрос надёжности при
реальной нагрузке, не демо-сценария.

**Риск, который остаётся.** Если MAX всё же ответит 429/5xx или временно недоступен — пользователь
получит `notified: false` в ответе API (уже реализовано), а не тихую потерю уведомления. Для
хакатон-демо это приемлемо; полноценный retry с backoff — первое, что стоит добавить для продакшена.

## 4. Нет полной дедупликации webhook по id

**Что сделано.** Вебхук отвечает `200 OK` даже если внутренняя обработка апдейта упала — ошибка
только логируется. Это защищает от retry-шторма при СВОИХ сбоях (MAX не будет бесконечно повторять
уже подтверждённый апдейт). Но если сам MAX по любой причине пришлёт один и тот же апдейт дважды —
это не будет замечено и обработается повторно.

**Почему не сделали полный дедуп.**
- Чтобы отличить повторный апдейт от нового, нужно хранить id уже обработанных апдейтов (отдельная
  таблица или кэш с TTL) и проверять его на каждый входящий запрос — до сих пор не было ни одного
  зафиксированного случая дублирования апдейтов от MAX в разработке/тестах, то есть мы бы строили
  защиту от гипотетического, а не наблюдаемого сценария.
- Часть практических последствий дублирования уже нейтрализована на уровне бизнес-логики без общего
  механизма дедупа: повторный клик "Откликнуться" на ту же вакансию блокируется уникальным
  ограничением `(vacancy_id, candidate_user_id)` в БД, повторная смена статуса на тот же статус
  теперь не создаёт повторной записи и не шлёт повторное уведомление (`unchanged: true`). Реальный
  риск от дублирования остаётся в основном для диалога создания вакансии (лишний шаг), что не ломает
  данные, максимум — раздражает пользователя лишним вопросом.

**Что это значит для фронта.** Не влияет на контракт API — это внутренняя надёжность обработки
входящих сообщений от MAX, фронта не касается напрямую.

## 5. Нет preview/confirm перед публикацией вакансии

**Что сделано.** В сценарии через бота вакансия публикуется сразу по завершении диалога из 6
вопросов — без промежуточного шага «проверьте и подтвердите». Через REST/мини-апп публикация — это
отдельный явный вызов `POST /api/vacancies/:id/publish` после создания черновика, то есть на уровне
API шаг подтверждения уже есть.

**Почему не добавили preview именно в бот-диалог.**
- Добавление шага предпросмотра в диалоговый сценарий бота — это новое состояние диалога (показать
  собранные данные текстом/карточкой, две кнопки "Опубликовать"/"Изменить", обработка "Изменить"
  с возвратом на нужный шаг). Это не мелкая правка, а расширение модели диалога, которое стоит
  отдельного отдельного времени и тестирования, чтобы не сломать уже работающий сценарий.
- Уже реализовано `PATCH /api/vacancies/:id` — редактирование черновика после создания. То есть
  ошибка в вакансии не фатальна: работодатель может создать её через бота и поправить любое поле
  через мини-апп (или повторно через REST) до того, как она понадобится кандидатам — жёсткого
  требования "нельзя публиковать неотредактированное" в текущем сценарии нет.

**Что это значит для фронта.** Если mini-app показывает форму создания/редактирования вакансии
отдельно от бот-диалога — там уже можно сделать свой preview-экран перед вызовом `publish`, это
не блокируется backend. Через бот-диалог вакансия действительно публикуется сразу.

## 6. Бенчмарк зарплаты — без сопоставления региона

**Что сделано.** Рыночный ориентир ищется в trudvsem.ru только по тексту должности (`category`),
без сопоставления свободного текста региона от пользователя со справочником кодов регионов
trudvsem. Ответ включает `vacancyCount` (размер выборки) и `isFresh` (кэш просрочен или нет), но не
включает явную привязку к региону/дату выборки в отдельных полях.

**Почему не сделали сопоставление региона.**
- У trudvsem.ru нет единого поискового API "по свободному тексту региона" — нужен собственный
  справочник соответствия (название региона/города от пользователя → код региона trudvsem), которого
  нет ни в открытом виде под рукой, ни времени его собрать и проверить на хакатоне. Без него
  "региональный" бенчмарк был бы либо неточным, либо требовал бы от пользователя выбирать регион
  из строго заданного списка — а это уже не тот UX, что в сценарии (свободный ввод региона в
  диалоге бота).
- Текущая реализация — это осознанно упрощённый, но честный ориентир: он показывает похожие
  вакансии по названию должности, помечен как best-effort (если trudvsem недоступен — просто
  не показывается, не блокирует публикацию), и число вакансий в выборке видно в ответе API.

**Что это значит для фронта.** Не показывать бенчмарк как точную региональную медиану — в подписи
у цифры стоит показывать что-то вроде «ориентир по N похожим вакансиям с "Работы России"», как
сейчас и делает бот в тексте сообщения (`formatBenchmarkText`).

## 7. Автоматических тестов нет

**Что сделано.** Проверка — вручную, через `test-data/` (примеры тел запросов + пошаговый сценарий
в `test-data/README.md`) и через живой диалог с ботом в MAX.

**Почему не написали тесты.**
- Время хакатона было потрачено на закрытие функциональных пробелов из аудита фронтенда (авторизация,
  корректность путей MAX API, гонки в статусах откликов, валидация, формат ошибок) — это то, что
  напрямую блокирует интеграцию фронта и то, что видит жюри на демо. Тесты не блокируют ни то, ни
  другое здесь и сейчас.
- Без тестов сейчас (учитывая объём ручной сверки, проведённой в этом раунде правок — построчный
  аудит каждого пункта хендоффа против реального кода) риск регрессии не нулевой, но управляемый.
  С тестами после хакатона — риск регрессии при дальнейшем развитии продукта будет специально
  снижаться, но это уже следующий этап, не MVP.

**Что это значит для фронта.** Не влияет на контракт — это только про надёжность дальнейшей
разработки backend, а не про то, что сейчас можно/нельзя вызывать.

Если что-то из этого списка окажется блокером для фронта в процессе интеграции (например, реально
понадобится region-aware бенчмарк или preview-шаг) — это не "невозможно", а конкретная новая задача
с понятной оценкой, которую можно взять в работу отдельно от уже сделанного.
