# Интеграция с backend

Основание: предоставленное ТЗ «Ассистент сезонного найма» (разделы 4–8). Backend в текущей рабочей ветке отсутствует. Описанный ниже auth-контракт — **предложение для согласования**, а не подтверждение существования серверного метода.

## Граница ответственности

- Frontend: MAX Bridge, отображение, маршрутизация, тема, передача исходной `initData` на сервер.
- Backend: проверка подписи и срока действия `initData`, создание сессии, права работодателя, доступ к своим вакансиям и откликам.
- Bot Gateway: бот-токен, вебхуки, диалоги, сообщения, публикация карточек, уведомления.
- Market Benchmark Client: запросы к «Работе России», кэш, метод расчёта показателей.

Ни токен бота, ни API-ключи не попадают в `VITE_*`. Frontend не вызывает MAX Bot API или trudvsem напрямую. `initDataUnsafe` не используется для выдачи доступа. Исходная `initData` не сохраняется в storage и не выводится в лог.

## Предлагаемый вход

Адрес задаётся `VITE_API_BASE_URL` + `VITE_AUTH_PATH`. По умолчанию путь пуст: приложение показывает состояние ожидания подключения и не обращается к придуманному endpoint.

Пример после согласования:

```env
VITE_API_BASE_URL=https://api.example.org
VITE_AUTH_PATH=/api/auth/max
```

```http
POST /api/auth/max
Content-Type: application/json

{"initData":"исходная строка window.WebApp.initData"}
```

```json
{
  "user": {
    "id": "internal-user-id",
    "max_user_id": "123456789",
    "display_name": "Анна",
    "role": "employer"
  }
}
```

Идентификаторы в этом предлагаемом DTO — строки, чтобы не терять точность больших ID. Ответ проверяется во время выполнения; `candidate` не даёт доступ к кабинету работодателя. В ТЗ `users.role` — последняя роль действия, поэтому backend должен отдельно подтвердить право работать в кабинете, а не считать это поле достаточной авторизацией. Этот вопрос нужно согласовать до подключения.

Предлагаемый способ сессии — HttpOnly cookie, выдаваемая сервером; frontend использует `credentials: include`. Сервер настраивает Secure, SameSite, ограниченный CORS и защиту изменяющих запросов от CSRF. Предпочтителен единый HTTPS-origin frontend и backend; cookie в cross-origin webview может блокироваться клиентом. Bearer-токены и их обновление сейчас не реализованы: при выборе такого протокола потребуется изменить адаптер.

Статусы: 401 — открыть приложение заново из бота; 403 — нет доступа работодателя; остальные неуспешные ответы — ошибка сервиса. Невалидный JSON/DTO — ошибка контракта. Тайм-аут запроса — 10 секунд; автоматического повторения POST нет, доступна явная повторная попытка. Размонтирование компонента отменяет запрос.

## Доменные типы и будущие методы

`src/entities/hiring.ts` отражает поля из ТЗ. Это заготовка доменных типов; реальные форматы ответов бизнес-методов ещё не подтверждены.

| Метод из ТЗ                                 | Будущая задача frontend                                                   |
| ------------------------------------------- | ------------------------------------------------------------------------- |
| `GET /api/vacancies?employer_id=`           | Список своих вакансий; сервер проверяет владельца независимо от параметра |
| `POST /api/vacancies`                       | Создание черновика                                                        |
| `GET /api/vacancies/{id}`                   | Детали вакансии                                                           |
| `POST /api/vacancies/{id}/publish`          | Подтверждение публикации карточки                                         |
| `POST /api/vacancies/{id}/close`            | Закрытие вакансии                                                         |
| `GET /api/vacancies/{id}/applications`      | Отклики                                                                   |
| `PATCH /api/applications/{id}`              | Смена статуса и серверное уведомление                                     |
| `GET /api/benchmark?region_code=&category=` | Рыночный ориентир                                                         |

Перед следующими этапами согласовать: обновление черновика (в ТЗ нет метода), оболочки ответов и пагинацию, формат ошибок, валюту/период оплаты, среднее или медиану бенчмарка, сроки сессии, повторную авторизацию после 401, допустимые переходы статусов.

## MAX: подтверждённая основа

- [MAX Bridge](https://dev.max.ru/docs/webapps/bridge): загрузка `https://st.max.ru/js/max-web-app.js`, исходная `initData`, `platform`, `BackButton.show/hide/onClick/offClick`.
- [MAX UI](https://dev.max.ru/ui): `@maxhub/max-ui`, провайдер `MaxUI`, компоненты `Button`, светлая и тёмная темы.
- [Введение](https://dev.max.ru/docs/webapps/introduction): мини-приложение подключается к боту, нужен HTTPS.

Тема следует `prefers-color-scheme` или выбору пользователя. Недокументированные `themeChanged`/`colorScheme` в Bridge не предполагаются. MAX UI автоматически выбирает оформление платформы. Системная «Назад» возвращает к обзору; на каждом внутреннем экране есть такой же доступный переход. Регистрация обработчика снимается при смене страницы.

## Проверка с настоящим ботом (после получения доступа)

1. Согласовать auth DTO и реализованный серверный метод, установить переменные окружения, пересобрать приложение.
2. Разместить `dist/` на HTTPS с SPA fallback на `index.html`; не запрещать embedding заголовком X-Frame-Options DENY.
3. Настроить URL мини-приложения у бота.
4. В мобильном и веб-клиенте MAX проверить вход, роль, тему, внутренние переходы и системную «Назад».
5. Проверить 401/403, недоступность backend, повторное открытие, отсутствие доступа по поддельной или просроченной `initData`.

Этот живой сценарий пока не выполнялся: данные бота и серверный auth-контракт ещё не предоставлены. Тестовый Bridge и ответы fetch в автоматических тестах не заменяют проверку внутри MAX.
