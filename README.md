# Сезон — ассистент сезонного найма в MAX

«Сезон» помогает небольшому бизнесу создавать вакансии, получать отклики и вести найм в MAX. Работник находит вакансии, оставляет контакт и следит за этапами своего отклика. Решение включает бота и мини-приложение с кабинетами работодателя и работника.

## Состояние проекта

| Проверка | Подтверждённый результат |
|---|---|
| Локальный и production Docker Compose | Сборка и запуск PostgreSQL, backend и frontend; все сервисы healthy |
| Автотесты на Node.js 22 | 209 backend и 310 frontend; все прошли |
| REST-сценарий через Nginx | 24 проверки на каждом варианте Compose; повтор после восстановления БД также успешен |
| База данных | Применяются 24 миграции; схема совпадает с Prisma |
| Контракт и шаблоны | OpenAPI валиден; Helm lint и template проходят |
| Внешний стенд | [HTTPS-интерфейс](https://5696077-bs94300.twc1.net), `/health` и защита API проверены |
| Полный сценарий в настоящем MAX | Требует отдельного прогона с двумя пользователями |

Доступный `/health` подтверждает процесс и соединение с БД. Он не проверяет токен бота, регистрацию webhook и доставку сообщений. Версия работающего backend на внешнем стенде отдельно не подтверждена.

**Перед публичным запуском:** задайте непустой случайный `SESSION_SECRET`. Текущий код принимает пустую строку как ключ подписи; при `SESSION_SECRET=` возможна подделка сессии. Также остаются уязвимости backend-зависимостей и несовпадение тайм-аутов бенчмарка. Эти проблемы описаны ниже и в аудите; обновление документации не исправляет код.

## Локальный запуск в Docker

Нужны работающий Docker и Docker Compose 2.24+. Команды выполняются из корня проекта. Для REST-проверки нужен Python 3.

Следующий запуск явно выбирает автономные настройки и не использует возможный `backend/.env` настоящего бота:

```sh
export COMPOSE_PROJECT_NAME=maxhack-local
export APP_NETWORK=maxhack-local
export HTTP_PORT=18080
export POSTGRES_PORT=15432
export BACKEND_ENV_FILE=./docker/config/backend.local.env

docker compose --env-file .env.example up --build --detach --wait
docker compose --env-file .env.example ps
curl --fail http://localhost:18080/health
```

Ожидаемый ответ: `{"ok":true,"db":"up"}`. Интерфейс доступен на `http://localhost:18080`, API — на том же адресе под `/api`. Порт backend 3000 внутри контейнера наружу не опубликован.

Автономный режим использует фиктивный токен и недоступный локальный адрес MAX API. Ошибка подключения к MAX в логе ожидаема. Производственная сборка интерфейса вне MAX показывает страницу входа; это не вход в рабочий кабинет. Проверка REST без MAX описана в [инструкции для жюри](test-data/README.md).

Compose создаёт сеть и том БД. Backend применяет миграции до запуска и работает от пользователя `node`. Frontend запускается после успешной проверки backend и БД.

Остановка с сохранением данных, с теми же переменными окружения:

```sh
docker compose --env-file .env.example down
```

`down --volumes` дополнительно удаляет БД выбранного Compose-проекта. Используйте его только для явно выделенного тестового окружения. Для нескольких стеков задавайте разные имя проекта, сеть и опубликованные порты.

## Настройка настоящего бота и production Compose

1. Создайте корневой `.env` из `.env.example`, задайте собственные реквизиты БД. Compose собирает из них URL: используйте URL-safe значения, например случайный пароль в hex. Изменение `.env` не меняет пароль уже созданного PostgreSQL-тома.
2. Создайте `backend/.env` из `backend/.env.example`. Заполните настоящий `MAX_BOT_TOKEN`, случайные `MAX_WEBHOOK_SECRET` и `SESSION_SECRET`, внешний HTTPS-адрес `PUBLIC_BASE_URL`.
3. Настройте TLS-прокси и открытие мини-приложения из бота. Для каждой среды используйте соответствующий публичный адрес; в `PUBLIC_BASE_URL` указывайте адрес без завершающего `/`.
4. Для публичного окружения оставьте `TEST_API_TOKEN` пустым, если фиксированный технический доступ не нужен. Секреты передавайте отдельно от репозитория.

Случайное значение для каждого секрета генерируется отдельно:

```sh
openssl rand -hex 32
```

После заполнения файлов:

```sh
docker compose --env-file .env -f docker-compose.prod.yaml config --quiet
docker compose --env-file .env -f docker-compose.prod.yaml up --build --detach --wait
```

Production Compose требует файл backend-окружения и не подставляет локальный фиктивный токен. Если ранее экспортирован `BACKEND_ENV_FILE`, он продолжает действовать: перед production-запуском удалите эту переменную или задайте путь к настоящему файлу. В контейнере Compose сам устанавливает `DATABASE_URL` с hostname `postgres` и `PORT=3000`.

Production публикует фиксированные порты 80 и 443, но стандартный Nginx-конфиг слушает HTTP на 80: сертификаты и TLS он не настраивает. Нужен внешний TLS-прокси либо собственный файл в `docker/config/nginx/`, выбранный через `NGINX_FILE`. При стандартном конфиге запрос к локальному 443 не работает. PostgreSQL в production не опубликован на хост.

Nginx направляет `/api/*`, `/webhook/max` и `/health` в backend, остальные пути обслуживает как SPA. После пересоздания только backend перезапустите frontend, чтобы Nginx заново определил адрес сервиса:

```sh
docker compose --env-file .env -f docker-compose.prod.yaml restart frontend
```

Для остановки, логов и любых дальнейших команд используйте тот же `-f`, `--env-file` и Compose project name, что при запуске.

## Переменные backend

| Переменная | Требование и назначение |
|---|---|
| `MAX_BOT_TOKEN` | Обязателен; настоящий токен для живого MAX, фиктивный — только для автономной проверки |
| `DATABASE_URL` | Подключение Prisma к PostgreSQL; для запуска вне Docker задаётся вручную |
| `MAX_API_BASE_URL` | По умолчанию `https://platform-api2.max.ru`; автономный режим намеренно использует недоступный локальный адрес |
| `MAX_WEBHOOK_SECRET` | Обязателен для публичного webhook; ожидается в `X-Max-Bot-Api-Secret`. При заданном `PUBLIC_BASE_URL` и пустом секрете webhook отвечает 503 |
| `PUBLIC_BASE_URL` | Публичный HTTPS-адрес без завершающего `/`; при старте backend пытается зарегистрировать `<адрес>/webhook/max` |
| `SESSION_SECRET` | Для публичного запуска задавайте собственный непустой случайный ключ. Если переменная отсутствует, ключ выводится из токена бота; пустая строка в текущем коде небезопасна |
| `TEST_API_TOKEN` | Необязательный доступ одного технического аккаунта; пустое значение отключает его. Не заменяет два аккаунта для проверки ролей |
| `MAX_BOT_USERNAME` | Username без `@` для ссылок отклика; без значения backend пытается получить его через `/me` |
| `FRONTEND_ORIGIN` | Разрешённые origin через запятую. При пустом значении разрешён любой origin; при общей точке входа Nginx междоменный CORS не нужен |
| `PORT` | По умолчанию 3000; Compose устанавливает 3000 явно |
| `TRUSTED_EMPLOYER_MIN_HIRES` | Порог подтверждённых наймов для отметки работодателя, по умолчанию 5 |

`backend/russian_ca_bundle.pem` — публичный CA bundle, подключаемый npm-скриптами и Docker-образом через `NODE_EXTRA_CA_CERTS`. Это не приватный ключ.

## Разработка вне Docker

Используйте поддерживаемую Node.js 22.22.2+ из ветки 22; в аудите проверена 22.23.4. Произвольная более новая major-версия не обязательно поддерживается зависимостями.

Сначала подготовьте `.env` и `backend/.env`, как описано выше. В `backend/.env` укажите `DATABASE_URL` с `localhost` и опубликованным портом PostgreSQL из корневого `.env` (по умолчанию 5446).

```sh
docker compose up --detach --wait postgres
cd backend
npm ci
npm run prisma:generate
npm run prisma:deploy
npm run dev
```

`prisma:deploy` применяет сохранённые миграции. `prisma:migrate` предназначен для разработки новой миграции, а не для воспроизведения готового проекта.

В другом терминале:

```sh
cd frontend
cp .env.example .env
npm ci
npm run dev
```

Для обращения Vite-интерфейса к локальному backend задайте в `frontend/.env` `VITE_API_BASE_URL=http://localhost:3000` и при необходимости `FRONTEND_ORIGIN=http://localhost:5173` в backend. Прокси `/api` в текущем `vite.config.ts` нет. Для живого MAX локальный HTTP не заменяет публичный HTTPS-стенд.

При `VITE_ENABLE_DEV_MODE=true` dev-сборка позволяет открыть демонстрационный кабинет без MAX. Данные в этом режиме подменены; он не проверяет сервер или доставку сообщений. В `build` и `preview` такой вход отключён.

Все `VITE_*` значения публичны и подставляются во время сборки. Их изменение в окружении уже запущенного Nginx не меняет готовый JS. Текущий frontend Dockerfile не принимает build-аргументы для них; стандартная сборка обращается к API через общий origin. Токен бота и серверные секреты нельзя помещать в frontend-переменные.

## Kubernetes / Helm

Chart создаёт Deployment, Service, ConfigMap и Ingress приложения. Отдельно необходимы PostgreSQL, ingress-контроллер, доступ к registry и Secret backend. По умолчанию используется Traefik; TLS завершается на внешнем прокси.

Проверка шаблонов без обращения к кластеру:

```sh
helm lint helm
helm template agile-project helm
```

Для установки подготовьте namespace `app`, Secret из `helm/backend-secret.example.yaml` и собственный файл values вне репозитория. Укажите:

- `global.registry`, репозитории и существующие теги обоих образов, `imagePullSecrets`;
- `backend.existingSecret` и `DATABASE_URL` доступной из кластера БД;
- токен бота, непустые ключ сессий и секрет webhook;
- `backend.config.PUBLIC_BASE_URL`, `ingress.host` и способ завершения TLS.

Пример команды для уже подготовленного окружения и опубликованных образов:

```sh
helm upgrade --install agile-project ./helm \
  --namespace app --create-namespace \
  --values /path/to/private-values.yaml \
  --wait --timeout 10m
```

В production выбирайте конкретные теги образов проверенного commit. Датированные теги по умолчанию в `helm/values.yaml` не гарантируют соответствия последнему коду. Backend допускает только одну реплику: фоновые задачи не координируются между процессами. Успешный `helm template` не подтверждает rollout или регистрацию бота. Файлы из `helm/examples/`, если они есть в рабочей копии, служат отдельными примерами внешнего окружения и автоматически chart не применяются.

## Основной пользовательский сценарий

1. Работодатель запускает личный чат с ботом и пишет `/новая_вакансия`.
2. Отвечает на семь вопросов: должность, сфера, регион, график, зарплата, требования и контакт.
3. Бот сохраняет **черновик** и показывает предпросмотр с кнопками «Опубликовать» и «Оставить черновиком». Публикация происходит только после подтверждения автора. При наличии данных выводится зарплатный ориентир.
4. Работодатель передаёт карточку кандидату. Для отклика из пересланной карточки используется ссылка в её тексте/deep link; username бота должен быть известен.
5. Кандидат открывает бота, оставляет контакт и получает подтверждение. Отклик появляется у работодателя, которому отправляется уведомление.
6. Работодатель меняет этап в мини-приложении. Сохранение этапа и доставка уведомления — отдельные результаты. Повтор того же этапа не создаёт повторного изменения.
7. Работодатель закрывает вакансию; новые отклики на неё запрещены.

`/отмена` сбрасывает диалог и ожидание контакта. Повторный отклик одного кандидата на одну вакансию блокируется уникальным ограничением БД.

Контакт работодателя не включается в публичную карточку; кандидат получает его после приглашения или найма. Форматы контактов frontend и backend пока различаются: интерфейс принимает телефон и MAX, сервер также допускает e-mail. Это открытое несоответствие, а не согласованный единый контракт.

Для живой приёмки нужны два настоящих пользователя MAX. Подробные шаги, ошибки и ожидаемые результаты — в [test-data/README.md](test-data/README.md).

## API и данные

REST использует JSON, bearer-авторизацию, snake_case в основных входных полях и camelCase в ответах. Даты — ISO 8601, суммы — целые рубли; отдельного периода оплаты в модели нет, в текущем продукте это месячная зарплата.

`POST /api/auth/max` проверяет подпись initData и выдаёт сессию на 30 дней. Отдельной роли пользователя в БД нет: режим кабинета выбирается в интерфейсе, а доступ к записям проверяется по владельцу из сессии. Один человек может и нанимать, и откликаться на чужие вакансии.

| Группа маршрутов | Назначение |
|---|---|
| `/health`, `/api/benchmark` | Публичная готовность сервера/БД и зарплатный ориентир |
| `/api/vacancies` | Свои вакансии, черновики, публикация, закрытие, статистика, QR |
| `/api/applications` | Создание отклика; список работодателя и смена этапа |
| `/api/jobs`, `/api/me/applications` | Каталог работника и история своих откликов |
| `/api/me` | Профиль, компания, контакт и прогресс доверия работодателю |
| `/api/regions`, `/api/categories`, `/api/badges` | Справочники; точные пути и требования авторизации — в OpenAPI |
| `/api/team`, `/api/vacancies/:id/team-invites` | Прошлые работники и повторное приглашение |
| `/api/me/subscriptions`, `/api/partner-channels` | Подписки и управляемые каналы партнёров |

Схемы и HTTP-коды приведены в [openapi.yaml](openapi.yaml), принятые решения — в [DECISIONS.md](DECISIONS.md). Типовая ошибка:

```json
{"error":{"code":"validation_error","message":"invalid request body","fields":{"title":["title is required"]}}}
```

Основные сущности: пользователи, вакансии, отклики и их события, сессии диалога, ожидание контакта, кэш бенчмарка, команда/приглашения, подписки/доставки, каналы/доставки. Полная структура и ограничения — в [schema.prisma](backend/prisma/schema.prisma).

Чат вакансии/отклика сохраняется отдельно от последнего чата пользователя. Личный `dialogChatId` устанавливается через `bot_started`; это снижает риск отправить персональное уведомление в группу. `candidate.maxContactUrl` берётся из ссылки MAX, оставленной в контакте отклика; URL из числового `maxUserId` не конструируется.

## Проверки и тестовые данные

```sh
cd frontend
npm ci
npm run lint
npm test
npm run build
```

Backend-тесты используют отдельную БД, имя которой обязательно заканчивается на `_test`. Они очищают таблицы; рабочую БД использовать нельзя. Доставка MAX в тестах подменена, миграции применяются автоматически.

```sh
cd backend
npm ci
npm run prisma:generate
npm run build
TEST_DATABASE_URL='postgresql://hiring:hiring_dev_password@localhost:5446/hiring_test?schema=public' npm test
```

Для другого опубликованного порта или реквизитов измените тестовый URL. Для проверки развёрнутого REST используйте [сценарий из 24 проверок](test-data/README.md). Он создаёт синтетические аккаунты, не публикует вакансию в MAX и не заменяет живую проверку.

Витрина для показа — `backend/prisma/seed-showcase.mjs`: вымышленные компании, вакансии, работники, бригада, смены и история. Скрипт запускается только с `ALLOW_SHOWCASE_SEED=true`, не отправляет сообщения при заполнении, повторно пересоздаёт свой набор без дублей. Он не должен автоматически запускаться на рабочей БД. Для локальной подготовленной БД после сборки:

```sh
cd backend
ALLOW_SHOWCASE_SEED=true npm run seed:showcase
```

`--owner-id=<id>` или `--owner-max-id=<MAX id>` привязывает часть витрины к существующему аккаунту, `--remove` удаляет витрину. Если затем менять этапы демо-кандидатов через приложение, настоящая доставка им невозможна. Не выдавайте данные витрины за реальные наймы или живую публикацию.

CI описан в [.github/workflows/ci.yml](.github/workflows/ci.yml): сборки, Prisma/миграции, backend/frontend-тесты, OpenAPI и проверки обоих Compose. После успешных проверок для master предусмотрены публикация образов и Helm deploy. Наличие workflow не доказывает успех конкретного удалённого запуска.

## Мониторинг

Не нужен для основного сценария. После запуска приложения создайте `monitoring/.env` из примера, задайте собственный пароль Grafana и передайте также корневой `.env` с реквизитами БД:

```sh
docker compose --env-file monitoring/.env --env-file .env \
  --project-name maxhack-monitoring \
  --file monitoring/docker-compose.yaml up --detach
```

Оба проекта должны использовать одну `APP_NETWORK`. Для production есть `monitoring/docker-compose.prod.yaml`. Собираются логи и метрики Nginx/PostgreSQL/компонентов мониторинга; `/metrics` приложения не реализован. Локальная Grafana занимает 3000, что конфликтует с backend вне Docker. Перед удалением сети приложения остановите мониторинг.
