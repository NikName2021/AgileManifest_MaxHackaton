# Тестовые данные

Примеры тел запросов для собственного API (см. `openapi.yaml` и `DATA-API.yaml` в корне
репозитория): `vacancy-create.json` (POST /api/vacancies), `vacancy-update.json` (PATCH
/api/vacancies/:id, частичное обновление черновика), `application-create.json` (POST
/api/applications).

## Сценарий проверки через REST API напрямую (без MAX)

Все запросы, кроме `GET /health` и `GET /api/benchmark`, требуют заголовок
`Authorization: Bearer <token>`. Для проверки без реального MAX-логина используйте
`TEST_API_TOKEN` из `backend/.env` — он маппится на фиксированного технического
пользователя (`test-jury-account`), от имени которого и будут создаваться вакансии/отклики.

1. Поднять стек: `docker compose up --build` (из корня репозитория).
2. Проверить, что сервис жив: `GET http://localhost:3000/health` → `{"ok": true, "db": "up"}`.
3. Создать вакансию: `POST http://localhost:3000/api/vacancies`, заголовок
   `Authorization: Bearer <TEST_API_TOKEN>`, тело — `vacancy-create.json`.
   Работодатель больше не передаётся в теле — это тот же пользователь, что и в токене.
4. Отредактировать черновик (опционально, только пока вакансия в статусе `draft`):
   `PATCH http://localhost:3000/api/vacancies/{id}`, тот же заголовок, тело — `vacancy-update.json`
   (частичное — например только `salary_min`/`salary_max`/`contact_info`). После публикации тот же
   запрос ответит `409`.
5. Опубликовать вакансию: `POST http://localhost:3000/api/vacancies/{id}/publish`
   (тот же заголовок). Публикация шлёт карточку в MAX в чат из `employer_chat_id` — у
   тестового пользователя жюри реального чата нет, поэтому эндпоинт ожидаемо ответит `502`
   (карточку отправить некуда) — сама вакансия при этом остаётся в статусе `draft`, это
   штатное поведение, не баг. Отклик на `POST /api/applications` ниже сработает и без публикации,
   если временно проверять P2002/валидацию отдельно от MAX-доставки.
6. Создать отклик: `POST http://localhost:3000/api/applications`, тот же заголовок, тело —
   `application-create.json`. Кандидат определяется токеном, а не полем в теле — при
   проверке одним и тем же `TEST_API_TOKEN` работодатель и кандидат будут одним и тем же
   пользователем; чтобы проверить отклик отдельно, выпустите вторую сессию через
   `POST /api/auth/max` с валидным `init_data` другого пользователя (или временно заведите
   второй тестовый токен).
7. Посмотреть воронку по одной вакансии: `GET http://localhost:3000/api/vacancies/{id}/applications`
   (только владелец вакансии получит 200, иначе 403; каждый отклик приходит с вложенным `candidate`).
8. Посмотреть общий список откликов по всем своим вакансиям, с пагинацией и фильтром:
   `GET http://localhost:3000/api/applications?status=new&limit=20&offset=0`.
9. Сменить статус отклика: `PATCH http://localhost:3000/api/applications/{id}`, тело
   `{"status": "invited"}`. Повторный такой же запрос ответит `200` с `"unchanged": true` и не
   пришлёт кандидату второе уведомление.
10. Проверить формат ошибки на любом из перечисленных запросов с намеренно неверным телом —
    ответ всегда вида `{"error": {"code": "...", "message": "...", "fields": {...}}}`, см.
    раздел «Решения по контракту» в README.md и схему `Error` в `openapi.yaml`.
