# Проверка решения для жюри

Есть два отдельных сценария: воспроизводимая проверка REST API на синтетических данных
и полный сценарий с настоящими пользователями MAX. Локальная проверка API не подтверждает
доставку карточек и уведомлений в MAX.

## 1. Локальная проверка API без MAX

Нужны Docker Compose 2.24+ и Python 3. Запускайте из корня репозитория.
Для проверки используйте отдельную тестовую БД, не базу с реальными пользователями.
Если `backend/.env` уже настроен на настоящего бота, `BACKEND_ENV_FILE` ниже явно выбирает
локальный режим без обращений к MAX.

```sh
export COMPOSE_PROJECT_NAME=maxhack-jury
export APP_NETWORK=maxhack-jury
export HTTP_PORT=18080
export POSTGRES_PORT=15432
export BACKEND_ENV_FILE=./docker/config/backend.local.env

docker compose up --build --wait
umask 077
docker compose exec -T -e ALLOW_DEMO_SEED=true backend \
  node prisma/seed-demo.mjs > .jury-access.json
python3 test-data/check-api.py \
  --base-url http://localhost:18080 --access-file .jury-access.json
```

Скрипт подготовки создаёт новый независимый набор при каждом запуске:

- синтетический аккаунт работодателя;
- синтетический аккаунт кандидата;
- вакансию работодателя со статусом `published`, установленным непосредственно в тестовой БД.

**Эта вакансия не публиковалась в MAX.** У аккаунтов нет чатов, поэтому внешние сообщения
не отправляются, ответы API содержат `notified: false`. Подготовка данных запускается
только явно через CLI; приложение не создаёт их при старте. Она использует стандартные
сессии приложения, не добавляет публичных способов обхода авторизации.

`.jury-access.json` содержит ID вакансии и отдельные bearer-токены двух аккаунтов.
Токены действуют до 30 дней при неизменном секрете подписи. Файл исключён из Git;
не прикладывайте его к публичным материалам и логам. Скрипт проверки токены не печатает.

Ожидаемый результат — `24 API checks passed`. При любой ошибке скрипт завершится с ненулевым кодом.
Он проверяет HTTP-коды, JSON и ключевые поля ответов, а также следующие действия:

| Действие | Ожидаемый результат |
|---|---|
| Проверка `/health` | `200`, `ok: true`, `db: up` |
| Запрос без авторизации | `401 unauthorized` |
| Невалидное тело запроса | `400 validation_error` |
| Создание и изменение черновика работодателем | `201 draft`, затем `200` с изменёнными полями |
| Чтение чужой вакансии кандидатом | `403 forbidden` |
| Публикация без известного чата работодателя | `409 employer_chat_missing`, черновик сохраняется |
| Отклик на черновик | `409 conflict` |
| Редактирование опубликованной вакансии | `409 conflict` |
| Отклик кандидата на подготовленную published-вакансию | `201 new`, `notified: false` |
| Повторный отклик | `409 conflict` |
| Просмотр откликов и пагинации работодателем | `200`, один созданный отклик |
| Доступ кандидата к чужой воронке или смене статуса | `403 forbidden` |
| Приглашение кандидата | `200 invited`, `notified: false` |
| Повторное приглашение | `200`, `unchanged: true` |
| Закрытие вакансии | `200 closed`; новый отклик и публикация закрытой вакансии — `409` |

Проверка закрывает подготовленную вакансию и создаёт собственный черновик и отклик.
Перед повторным прогоном ещё раз запустите `seed-demo.mjs` и обновите файл доступов.
Остановка и полное удаление **только отдельного тестового проекта**, с сохранёнными выше переменными:

```sh
docker compose down --volumes --remove-orphans
rm .jury-access.json
```

## 2. Проверка вручную через REST

Для обычного локального Compose используйте `http://localhost` либо заданный `HTTP_PORT`.
Backend на порту 3000 внутри Docker не опубликован на хост. На развёрнутом стенде используйте
его HTTPS-адрес. Скрипт также принимает этот адрес через `--base-url`, но только для
выделенных синтетических аккаунтов, подготовленных оператором стенда.

В `.jury-access.json` используйте `employer.token` для действий работодателя и
`candidate.token` для действий кандидата. Заголовок: `Authorization: Bearer <соответствующий токен>`.
`POST`/`PATCH` с JSON требуют `Content-Type: application/json`. Токены различаются;
роль определяется владением записью, а не отдельным полем `role`.

Примеры тел: `vacancy-create.json`, `vacancy-update.json`, `application-create.json`.
В последнем замените демонстрационный `vacancy_id: 1` на `published_vacancy_id` из файла доступов.
При проверке черновика используйте ID из ответа `POST /api/vacancies`.

`TEST_API_TOKEN`, если задан, представляет только один технический аккаунт и не заменяет
пару работодатель/кандидат. У него нет настоящего чата MAX: публикация может завершиться
`502 upstream_error` при отказе MAX, а при отсутствии чата — `409 employer_chat_missing`.
На неопубликованную вакансию откликнуться нельзя (`409`). Не меняйте код или проверки
авторизации ради прохождения сценария.

## 3. Полный сценарий в MAX — после развёртывания

Предусловия: работающий HTTPS-стенд, настоящий токен бота, `PUBLIC_BASE_URL`,
`MAX_WEBHOOK_SECRET`, настроенный вход в мини-приложение. Ссылку на бота и проверочные
доступы организатор передаёт жюри отдельно. Нужны два разных пользователя MAX.

1. Работодатель открывает личный чат с ботом и пишет `/новая_вакансия`.
2. Проходит диалог. В чате появляется настоящая карточка вакансии с кнопкой отклика;
   вакансии соответствует статус `published`. При доступности «Работы России» показан бенчмарк;
   отсутствие данных должно явно отображаться, без выдуманных рыночных значений.
3. Работодатель передаёт карточку кандидату. Кандидат открывает кнопку/deep link,
   переходит в личный чат с ботом и передаёт свой контакт.
4. Кандидат получает подтверждение, работодатель — уведомление с откликом.
5. Работодатель открывает мини-приложение: видит свою вакансию и отклик.
   Меняет статус на «Приглашён». Кандидат получает уведомление.
6. Повторное нажатие «Приглашён» не отправляет второе уведомление;
   повторный отклик не создаёт дубликат.
7. Работодатель закрывает вакансию. Новый отклик на закрытую вакансию отклоняется.
8. Повторить основной путь в мобильной и веб-версии MAX. Проверить отмену диалога
   и понятную обработку ошибки/некорректного ввода.

Для проверки настоящего REST publish создайте черновик от сессии реального работодателя,
который уже написал боту, и вызовите `POST /api/vacancies/{id}/publish`: ожидается `200`
и карточка в чате. Данные `seed-demo.mjs` для этого не подходят.

## Перед передачей материалов

В `DATA-API.yaml` заполнить `api.base_url` реальным HTTPS-адресом, заменить статус
`deployment_pending` после проверки стенда. Сверить контракт с `openapi.yaml` и отдельно
выданной схемой организаторов, если она есть. Указать ссылку на бота, commit hash,
проверочные доступы и краткий сценарий на служебном слайде презентации. Рабочие секреты
не публиковать в репозитории. До развёртывания живой сценарий остаётся непроверенным.
