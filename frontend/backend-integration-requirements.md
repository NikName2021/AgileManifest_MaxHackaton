# Контракт бэкенда для изменений фронтенда

Дата: 24 октября 2026 года.

Изменения серверного кода выполняет разработчик бэкенда. Этот документ фиксирует требования фронтенда и проверки совместимости; он не означает, что серверные изменения уже развёрнуты.

По сообщению разработчика бэкенда, уведомления, антиспам, запрет ручного статуса «Новый», справочник сфер, отдельный признак для студентов и запрет Telegram уже реализованы. Повторно реализовывать их не нужно — следует сверить фактический API с требованиями ниже.

## Статусы отклика

- `new` назначается только при создании отклика.
- `PATCH /api/applications/:id` принимает для смены этапа только `contacted`, `invited`, `hired`, `rejected`.
- Попытка вручную установить `new` возвращает `400 validation_error` с ошибкой поля `status`, не меняет запись и не отправляет уведомление.
- То же ограничение действует для callback-кнопок бота и общей функции смены этапа.
- Фильтрация и чтение откликов со статусом `new` сохраняются.

Фронтенд убрал кнопку «Новый» из выбора этапа и сохраняет её в фильтрах.

## Результат уведомления

Фронтенд читает необязательное строковое поле `notification` в ответе на смену этапа вместе с существующими `notified`, `unchanged`, `vacancyClosed` и данными отклика:

| Значение | Сообщение работодателю |
| --- | --- |
| `deferred` | Кандидату придёт сообщение через пару минут с итоговым этапом. |
| `no_chat` | Кандидат не запускал бота. Попросите его нажать «Начать» в боте MAX. |

Если `notification` отсутствует, используется прежний флаг `notified`. Для этапа «На связи» уведомление теперь также ожидается. Ошибка доставки не должна отменять сохранённый этап. Неизвестный новый строковый код не мешает фронтенду обработать успешное сохранение.

Антиспам и доставка, в том числе попытка по `user_id`, остаются ответственностью бэкенда. Реальную доставку в MAX необходимо проверять отдельно; фронтенд её не подтверждает самостоятельно.

## Сфера деятельности

- Источник допустимых значений — `GET /api/categories`, включая сферы без опубликованных вакансий.
- Подсказки `GET /api/categories/suggest` могут распознавать синонимы и опечатки; фронтенд предлагает только значения из основного справочника.
- Неизвестный текст не должен автоматически превращаться в «Другое». Этот вариант выбирается явно.
- Ошибка `400 validation_error` должна содержать поле `category`, чтобы фронтенд показал её непосредственно под полем.
- Для существующей категории «Другое» старый `categoryDetail` не подставляется фронтендом вместо значения справочника при редактировании.

## Подходит студентам

- Запись: отдельный boolean `student_friendly`; чтение: `studentFriendly`.
- Признак не входит в массив выбранных `badges` и не занимает место в лимите 10 бейджей.
- Создание вакансии и частичное обновление должны разрешать 10 обычных бейджей вместе с `student_friendly: true`; 11 обычных бейджей должны отклоняться.
- `students_ok` не предлагается в справочнике выбора бейджей.
- Старые вакансии с `students_ok` переводятся на отдельный признак миграцией бэкенда. Фронтенд также умеет читать старое представление и при следующем сохранении передаёт boolean без этого ключа в `badges`.
- Карточка сообщения бота показывает отдельную строку «🎓 Подходит студентам».

## Контакты работника и работодателя

По требованию пользователя фронтенд разрешает только телефон, `@ник` в MAX и ссылку на `max.ru` / `web.max.ru`. Для работодателя поддерживаются до трёх контактов в одном поле.

Сверить это ограничение для `contact_info` вакансии, `contact` отклика, `application_contact` профиля и ввода в диалоге бота. Удаление сохранённого необязательного контакта должно оставаться доступным.

**Пункт для отдельной сверки:** в сообщении бэкенда подтверждён запрет `t.me` и `telegram.me`, но не уточнён запрет e-mail, VK, WhatsApp и других внешних сервисов. Фронтенд их отклоняет согласно требованию «только номер и MAX». Нужно подтвердить такую же серверную политику. Внешние ссылки с подменой домена, например `max.ru.evil.test`, недопустимы.

Голый `@ник` не содержит признака платформы: фронтенд подписывает его как MAX, но по одной строке проверить принадлежность аккаунта невозможно. Старые сохранённые контакты не следует удалять автоматически.

Подсказки бота и демоданные при необходимости привести к той же политике. Проверки контактов в описаниях и других полях, не предназначенных для связи, должны продолжать работать.

## Проверки бэкенда

1. Сброс этапа в `new` через REST и callback не меняет запись и не создаёт уведомлений; остальные разрешённые этапы работают.
2. `deferred` и `no_chat` возвращаются в согласованном формате без потери сохранённого этапа.
3. Неизвестная сфера возвращает ошибку поля `category`; «Другое» принимается явно.
4. 10 обычных бейджей и студенческий флаг принимаются как при создании, так и при PATCH.
5. Телефон и MAX принимаются, Telegram и остальные несогласованные форматы отклоняются во всех точках ввода; необязательный контакт можно очистить.

Мои серверные изменения из коммита `68adcef` отменены отдельным исправляющим коммитом. Этот документ заменяет их как перечень требований и проверок для разработчика бэкенда.
