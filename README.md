# МаксХак — Ассистент сезонного найма (трек «Эффективный бизнес»)

Чат-бот в MAX для небольшого сезонного/локального бизнеса: помогает быстро составить вакансию, показывает рыночный бенчмарк по данным «Работы России», публикует карточку вакансии с кнопкой «Откликнуться» и ведёт простую воронку найма прямо в чате.

## Структура и архитектура

```text
MAX / браузер → Nginx → Fastify API → PostgreSQL (Prisma)
                          ├→ MAX Bot API: карточки и уведомления
                          └→ «Работа России»: зарплатный бенчмарк, кеш 24 часа
```

- `backend/` — Node.js, TypeScript, Fastify, Prisma; вебхук и REST API.
- `frontend/` — мини-приложение «Сезон»: React, TypeScript, Vite, MAX Bridge.
- `docker-compose.yaml`, `docker-compose.prod.yaml` — локальный и production-стек.
- `docker/config/nginx/` — раздача frontend и проксирование API/вебхука.
- `monitoring/` — необязательный мониторинг, не нужен для основного сценария.
- `openapi.yaml` — контракт API; `DATA-API.yaml` — описание проверок для сдачи.
- `test-data/` — примеры JSON, автоматическая проверка API и сценарий для жюри.
- `backend/prisma/seed-demo.mjs` — явная подготовка синтетических данных для проверки.

MAX — внешний сервис: живой сценарий требует токена бота, HTTPS-адреса и пользователей MAX.
«Работа России» запрашивается по сети; отсутствие данных не заменяется выдуманными значениями.
Пользователи, вакансии, отклики, диалоги и кеш сохраняются в PostgreSQL и переживают
пересоздание контейнеров при сохранении именованного тома.

## Быстрый старт (локальная разработка)

Нужны Node.js 22.22.2+ и Docker Compose 2.24+.

```sh
cp .env.example .env
cp backend/.env.example backend/.env
# В backend/.env заполнить MAX_BOT_TOKEN; DATABASE_URL должен соответствовать
# POSTGRES_USER, POSTGRES_PASSWORD, POSTGRES_DATABASE и POSTGRES_PORT из .env.
docker compose up -d postgres
cd backend
npm ci
npm run prisma:generate
npm run prisma:migrate
npm run dev
```

Backend вне Docker слушает `http://localhost:3000`. Для frontend отдельно выполните
`npm ci` и `npm run dev` в каталоге `frontend`.

### Про сертификат `backend/russian_ca_bundle.pem`

Это не секрет — публичный сертификат «Минцифры» (Russian Trusted Root CA + Sub CA, gosuslugi.ru/crt), без него Node.js на Windows не может установить HTTPS-соединение с `platform-api2.max.ru`. Файл специально закоммичен в репозиторий и подключается автоматически через `NODE_EXTRA_CA_CERTS` в npm-скриптах (`backend/package.json`) — ничего дополнительно настраивать не нужно.

### Полный стек в Docker

```sh
docker compose up --build --wait
```

Из чистого checkout запускаются PostgreSQL, backend и frontend на `http://localhost`.
По умолчанию используется локальный режим без подключения к MAX: настройки из
`docker/config/backend.local.env` содержат тестовый токен и недоступный локальный адрес API.
Ошибка подключения к MAX в логе в этом режиме ожидаема; API, БД и интерфейс доступны,
но вход через MAX и отправка сообщений не работают.

Для настоящего бота скопируйте `backend/.env.example` в `backend/.env`, заполните токен,
`MAX_WEBHOOK_SECRET`, `SESSION_SECRET`, `PUBLIC_BASE_URL` и при необходимости `FRONTEND_ORIGIN`.
Значения этого файла перекрывают локальные настройки. `DATABASE_URL` и `PORT` внутри
контейнера задаёт Compose: БД доступна по имени `postgres`, backend слушает порт 3000.
Корневой `.env` настраивает PostgreSQL, `HTTP_PORT` (по умолчанию 80), `POSTGRES_PORT`
(по умолчанию 5446), `NGINX_FILE` и имя сети `APP_NETWORK` (по умолчанию `max_hackathon`).
Логин, пароль и имя БД должны быть URL-safe, поскольку Compose собирает из них `DATABASE_URL`.
Не меняйте реквизиты существующего тома БД без соответствующих изменений в PostgreSQL.

Сеть создаётся автоматически. Backend применяет сохранённые Prisma-миграции и запускается
от пользователя `node`; frontend стартует после успешного `/health` с проверкой БД.
Nginx обслуживает SPA и передаёт `/api/*`, `/webhook/max`, `/health` в backend.
Для нескольких независимых локальных стеков задайте разные `-p`, `APP_NETWORK`, `HTTP_PORT` и `POSTGRES_PORT`.
Nginx определяет адрес backend при старте. После отдельного пересоздания backend выполните
`docker compose restart frontend`, чтобы Nginx заново определил его IP.

Production запускается отдельно:

```sh
# Подготовить корневой .env с реквизитами БД и backend/.env с настройками настоящего бота.
docker compose --env-file .env -f docker-compose.prod.yaml up --build --wait
```

Production не использует локальный тестовый токен: `backend/.env` обязателен.
Путь к нему можно переопределить через `BACKEND_ENV_FILE`. Конфигурация HTTPS остаётся
в ведении окружения развёртывания; этот Compose не настраивает TLS. Production публикует
фиксированные порты 80 и 443, а PostgreSQL доступен только внутри Docker-сети. После
пересоздания backend перезапустите frontend с теми же `--env-file` и `-f` параметрами.

### Мониторинг

Сначала запустите приложение, затем подготовьте `monitoring/.env` из примера. При запуске
передавайте также корневой `.env`, чтобы экспортер PostgreSQL использовал те же реквизиты:

```sh
cp monitoring/.env.example monitoring/.env
# Задать пароль Grafana в monitoring/.env.
docker compose --env-file monitoring/.env --env-file .env -p maxhack-monitoring -f monitoring/docker-compose.yaml up -d
```

Для production используйте `monitoring/docker-compose.prod.yaml` и задайте параметры Grafana
из `monitoring/.env.example`. Оба варианта подключаются к сети `APP_NETWORK`, созданной приложением.
Собираются логи контейнеров, метрики Nginx, PostgreSQL и компонентов мониторинга. Redis и сбор
несуществующего backend `/metrics` удалены; метрики приложения можно добавить после реализации
этого эндпоинта. Перед остановкой приложения с удалением сети сначала остановите мониторинг.

## Основной пользовательский сценарий (проверяется в MAX)

1. Работодатель пишет боту `/новая_вакансия`.
2. Отвечает на 6 вопросов (должность, регион, график, зарплата, требования, контакт).
3. Бот сохраняет вакансию, публикует карточку с кнопкой «Откликнуться» и показывает рыночный
   ориентир по зарплате (данные trudvsem.ru «Работа России», с кэшем на 24 часа).
4. Кандидат нажимает «Откликнуться» на карточке — бот сохраняет отклик и уведомляет работодателя
   в чате. Если карточка переслана в чат/группу, где бота нет, на карточке есть вторая кнопка —
   deep-link, открывающий приватный чат с ботом и продолжающий тот же сценарий отклика.
5. Повторный отклик того же кандидата на ту же вакансию отклоняется (защита на уровне БД).

Отменить диалог на любом шаге — команда `/отмена` (сбрасывает и диалог создания вакансии, и
ожидание контакта после «Откликнуться», если оно было активно).

## Переменные окружения (`backend/.env`, см. `backend/.env.example`)

| Переменная | Обязательна | Назначение |
|---|---|---|
| `MAX_BOT_TOKEN` | да | Токен бота, выдаётся организаторами хакатона |
| `MAX_API_BASE_URL` | нет (есть значение по умолчанию) | Базовый URL MAX Bot API — `https://platform-api2.max.ru` |
| `MAX_WEBHOOK_SECRET` | нет | Секрет для проверки входящих вебхуков (передаётся MAX в заголовке `X-Max-Bot-Api-Secret`) |
| `PUBLIC_BASE_URL` | нет, но нужен для живого теста в MAX | Публичный HTTPS-адрес backend (например, ngrok-туннель) — если задан, бот при старте сам регистрирует вебхук-подписку в MAX на `<PUBLIC_BASE_URL>/webhook/max` |
| `DATABASE_URL` | да | Строка подключения к Postgres |
| `PORT` | нет (по умолчанию 3000) | Порт, на котором слушает backend |
| `SESSION_SECRET` | нет (иначе выводится из `MAX_BOT_TOKEN`) | Секрет для подписи сессионных токенов мини-приложения |
| `TEST_API_TOKEN` | нет, но нужен для проверки REST API жюри | Фиксированный bearer-токен для тестирования без реального MAX-логина (`Authorization: Bearer <TEST_API_TOKEN>`) |
| `MAX_BOT_USERNAME` | нет (backend определяет сам через `/me`) | Username бота без `@` — нужен для deep-link кнопки на карточке вакансии |
| `FRONTEND_ORIGIN` | нет (без него CORS разрешает любой origin) | Origin(ы) frontend через запятую — нужен, чтобы браузер/WebView мини-аппа с отдельного домена мог слать запросы с заголовком `Authorization` (CORS) |
| `TRUSTED_EMPLOYER_MIN_HIRES` | нет (по умолчанию 5) | Сколько разных людей должны подтвердить выход на работу, чтобы работодатель получил отметку «Надёжный работодатель». Для демо можно снизить |

## Порты

- `80` — frontend, API и вебхук через Nginx; в локальном Compose меняется через `HTTP_PORT`.
- `443` — опубликован в production; TLS требует отдельной настройки при развёртывании.
- `3000` — backend внутри Docker-сети; для запуска вне Docker настраивается через `PORT`.
- `5446` — PostgreSQL на хосте только в локальном Compose (`POSTGRES_PORT`); в production наружу не опубликован. Внутри сети — `5432`.

## Модель данных

| Таблица | Ключевые поля | Назначение |
|---|---|---|
| `users` | `id`, `max_user_id`, `chat_id`, `dialog_chat_id` (nullable), `display_name`, `phone` (nullable), `application_contact` (nullable) | Все пользователи бота |
| `vacancies` | `id`, `employer_user_id`, `title`, `region_code`, `category`, `schedule`, `salary_min`, `salary_max`, `description`, `contact_info`, `status` (draft/published/closed), `card_message_id`, `employer_chat_id`, `created_at`, `published_at`, `reminder_sent_at` | Вакансии, созданные через бота или мини-приложение |
| `applications` | `id`, `vacancy_id`, `candidate_user_id`, `status` (new/contacted/invited/hired/rejected), `contact`, `candidate_chat_id`, `hired_at`, `created_at`, `updated_at` | Отклики кандидатов и статус воронки |
| `benchmark_cache` | `region_code`, `category`, `avg_salary_min`, `avg_salary_max`, `vacancy_count`, `fetched_at` | Кэш ответов trudvsem, TTL 24 часа |
| `dialog_sessions` | `chat_id`, `step`, `data`, `updated_at` | Текущий шаг диалога создания вакансии (переживает рестарт backend) |
| `pending_applications` | `chat_id`, `vacancy_id`, `created_at` | Ожидание контакта от кандидата после нажатия «Откликнуться», до сохранения отклика |
| `team_invites` | `vacancy_id`, `candidate_user_id`, `status` (sent/accepted/declined/expired/undelivered), `created_at`, `responded_at` | Приглашения прошлых работников на новую вакансию («Моя бригада») |
| `team_marks` | `employer_user_id`, `candidate_user_id`, `reliable` | Отметка работодателя «надёжный» |
| `job_subscriptions` | `user_id`, `region_subject`, `category`, `schedule`, `salary_from`, `student_only` | Подписки кандидатов на новые вакансии (до 5 на человека) |
| `subscription_deliveries` | `vacancy_id`, `user_id` | Кому вакансия уже разослана по подписке |
| `partner_channels` | `chat_id`, `title`, `owner_user_id`, `active`, `region_subject`, `student_only`, `removed_at` | Каналы и чаты партнёров, куда добавлен бот |
| `channel_deliveries` | `vacancy_id`, `channel_id` | В какие каналы вакансия уже опубликована |

С v0.6.0 у `vacancies` также есть `region_subject` (код субъекта РФ), `headcount`, `student_friendly`;
у `applications` — `source` (откуда отклик), `start_at`, `shift_note`, `attendance`,
`attendance_reminder_sent_at`; у `pending_applications` — `source`.

`employer_chat_id` и `candidate_chat_id` — чат MAX, застывший один раз в момент публикации/отклика
и используемый для всех будущих уведомлений по этой вакансии/отклику. Это отдельно от «текущего»
`users.chat_id`, который обновляется на последний чат, откуда пользователь писал боту (нужен для
самого диалога) — без разделения уведомление могло бы случайно уйти в другой чат/группу.

`vacancies.contact_info` — контакт работодателя для откликнувшихся (телефон или юзернейм MAX),
отдельное структурированное поле (раздел 3.3 хендоффа фронтенда), а не часть свободного текста
`description` — раньше контакт дописывался прямо в описание и REST не мог отдать/принять его
отдельно. Показывается отдельной строкой на карточке вакансии.

`users.dialog_chat_id` — личный чат пользователя с ботом. Проставляется только из события
`bot_started` (по документации MAX deep link и «Начать» открывают приватный чат), в отличие от
`chat_id`, который может оказаться групповым. Уведомления кандидату о статусе отклика идут в
`applications.candidate_chat_id`, а если его нет — только в `dialog_chat_id`, но не в группу.
`users.application_contact` — сохранённый контакт для предзаполнения формы отклика в кабинете
работника; не заменяет `phone` (номер из MAX) и не переписывает контакты уже отправленных откликов.

## Решения по контракту (важно для фронтенда)

По итогам разбора вопросов, присланных фронтенд-разработчиком по предыдущей версии API, приняты
и зафиксированы такие решения:

- **Роль пользователя.** Отдельного поля `role` в `users` нет. Любой авторизованный пользователь
  может и создавать/публиковать вакансии (выступать работодателем), и откликаться на чужие
  (выступать кандидатом) — в один и тот же момент. Доступ к конкретной записи определяется
  владением (`employerUserId` у вакансии, `candidateUserId` у отклика), а не ролью аккаунта.
  Если для финала понадобится разделение ролей — это отдельное расширение схемы, текущую
  интеграцию оно не блокирует.
- **Формат сессии.** `Authorization: Bearer <token>`, а не `HttpOnly`-cookie. Если существующий
  адаптер фронтенда рассчитан на cookie — его нужно переключить на заголовок.
- **Идентификаторы и числа.** `:id` в пути — положительное целое, иначе `400 validation_error`.
  `salary_min`/`salary_max` в теле — JSON-числа: строки (`""`, `"50000"`) отклоняются, а не
  превращаются в 0.
- **Кандидат в ответах работодателя.** `candidate` в `GET /api/applications`,
  `GET /api/vacancies/:id/applications` и `PATCH /api/applications/:id` содержит только
  `id`, `maxUserId`, `displayName`, `phone`; ответ `PATCH` также содержит `vacancy { id, title, status }`.
- **Формат ошибок.** Единый на весь API конверт:
  ```json
  { "error": { "code": "validation_error", "message": "invalid request body", "fields": { "title": ["title is required"] } } }
  ```
  `code` — одно из: `unauthorized`, `forbidden`, `not_found`, `validation_error`, `conflict`,
  `upstream_error`, `service_unavailable`, `internal_error`, `employer_chat_missing`,
  `card_delivery_unknown`, `self_application_forbidden`, `vacancy_unavailable`,
  `already_applied`. `fields` присутствует только при
  `validation_error`, когда ошибку можно привязать к конкретным полям. См. `backend/src/errors.ts`
  и схему `Error` в `openapi.yaml`.

## Остановка и перезапуск

```
docker compose down          # остановить контейнеры, данные в volume сохраняются
docker compose down -v       # остановить и полностью стереть данные Postgres
docker compose up -d         # запустить снова (без пересборки)
docker compose up --build    # запустить с пересборкой образов
```

Для локальной разработки без Docker (`npm run dev`) — остановка обычным `Ctrl+C`, БД (запущенная через `docker compose up -d postgres`) отдельно останавливается той же командой `docker compose down`.

## Собственный API

REST/JSON, авторизация — bearer-токен (`Authorization: Bearer <token>`): либо сессия,
выданная через `POST /api/auth/max` (проверка подписи `initData` мини-приложения MAX), либо
фиксированный `TEST_API_TOKEN` из `.env` — для проверки жюри без реального MAX-логина.
`GET /health` и `GET /api/benchmark` авторизации не требуют. Работодатель/кандидат
определяются по токену, а не по полям тела запроса — эндпоинты возвращают только данные,
принадлежащие вызывающему (403 на чужие вакансии/отклики). Полный список ручек, схемы и коды
ответов — в [`openapi.yaml`](openapi.yaml) и [`DATA-API.yaml`](DATA-API.yaml). Примеры запросов
и пошаговый сценарий проверки напрямую через API (без MAX) — в
[`test-data/README.md`](test-data/README.md). Формат ошибок и остальные принятые решения по
контракту — см. раздел «Решения по контракту» выше.

CORS настроен через `FRONTEND_ORIGIN` (см. таблицу переменных окружения) — без него разрешён
любой origin (удобно для разработки/жюри), с ним — только перечисленные, для запросов с
`Authorization` и `Content-Type` методами `GET/POST/PATCH/OPTIONS`.

Помимо CRUD по вакансиям и откликам из первой версии, в API есть:
- `PATCH /api/vacancies/:id` — редактирование черновика (только в статусе `draft`, 409 иначе);
- `GET /api/applications` — общий список откликов по всем вакансиям работодателя, с пагинацией
  (`limit`/`offset`) и фильтром по `status`, в дополнение к `GET /api/vacancies/:id/applications`
  (отклики по одной вакансии, без пагинации).

### Кабинет работника (v0.4.0)

После входа мини-приложение предлагает режим «работодатель» или «работник». Режим — выбор
интерфейса на frontend, на сервере он не хранится и прав не даёт: один аккаунт MAX может и
нанимать, и откликаться, доступ проверяется по userId из сессии и владению записью. Прежние
маршруты работодателя (`/api/vacancies`, `GET /api/applications`) не изменили назначения.

| Маршрут | Назначение |
|---|---|
| `GET /api/jobs` | Каталог: только `published` и только чужие вакансии; `q`, `region_code`, `category`, `schedule`, `salary_from`/`salary_to` (пересечение диапазонов), `sort=newest\|salary_desc`, `limit` 1–100 (20), `offset`. Ответ `{ items, total, limit, offset }`, у каждой — `myApplication`, `canApply`, `applyUnavailableReason` |
| `GET /api/jobs/filters` | `{ regions, categories }` из реально доступных вакансий; `label = value` (справочника названий нет) |
| `GET /api/jobs/:id` | Карточка для работника; черновик/закрытая/нет — `404 not_found`; своя — `canApply=false`, `own_vacancy` |
| `POST /api/applications` | Отклик (прежний маршрут): `contact` теперь обязателен, коды `self_application_forbidden` (403), `vacancy_unavailable`, `already_applied` (409) |
| `GET /api/me/applications` | История своих откликов (включая закрытые вакансии) с `vacancy.contactInfo` работодателя |
| `GET /api/me`, `PATCH /api/me` | Профиль `{ id, displayName, applicationContact, hasBotChat }`; PATCH принимает только `application_contact` |

Зарплаты — целые рубли; период в модели не хранится, по смыслу продукта это рубли в месяц (как и
бенчмарк «Работы России»). При появлении оплаты за смену/час нужно отдельное поле `salary_period`.

Отклик через REST и через бота идёт через одну функцию `createApplicationRecord`
(`backend/src/application/service.ts`): проверка статуса и вставка — в транзакции под
`SELECT … FOR SHARE` на строку вакансии, дубли отсекает уникальный индекс. Поэтому одинаково
работают запрет отклика на свою вакансию, повторы (в т.ч. параллельные и REST + бот) и гонка с
закрытием вакансии.

**Текстовая ссылка в карточке.** MAX не переносит inline-кнопки при пересылке сообщения бота,
поэтому в конец текста карточки добавляется `Откликнуться:` и ссылка
`https://max.ru/<botUsername>?start=apply_<id>` (кнопки исходного сообщения сохраняются). Длина
карточки при создании/редактировании считается с резервом под ссылку, перед отправкой текст
проверяется ещё раз. Если username бота неизвестен (не определился через `GET /me` и не задан
`MAX_BOT_USERNAME`), карточка уходит без ссылки и в лог пишется предупреждение — битый URL не
вставляется. Уже отправленные карточки не меняются; ссылку для них работодатель получает из поля
`applyUrl` в `GET /api/vacancies` / `GET /api/vacancies/:id` и пересылает вручную (или закрывает
вакансию и публикует новую). Массовой рассылки обновлений нет.

### «Моя бригада» (v0.5.0)

Сезонный бизнес каждый год ищет во многом тех же людей. Бригада — все, кого работодатель уже
нанимал (статус `hired`) на своих вакансиях.

| Маршрут | Назначение |
|---|---|
| `GET /api/team` | Бригада: по одному элементу на человека — контакт из прошлого отклика, сколько раз нанимали, последняя вакансия, отметка «надёжный», `hasBotChat` |
| `PATCH /api/team/:id` | `{ "reliable": true }` — отметить прошлого работника; надёжные выводятся первыми |
| `POST /api/vacancies/:id/team-invites` | Позвать всю бригаду (или `candidate_ids`) на опубликованную вакансию; результат по каждому человеку: `sent`, `already_invited`, `already_applied`, `no_bot_chat`, `not_in_team`, `delivery_failed`, `limit_exceeded` |
| `GET /api/vacancies/:id/team-invites` | Кто приглашён и что ответил: `sent`, `accepted`, `declined`, `expired`, `undelivered` |

Человек получает в личный чат с ботом сообщение с кнопками «Приду» / «Не в этот раз». «Приду»
сразу создаёт отклик со статусом `invited` и тем контактом, который он оставлял этому работодателю
раньше, а работодателю приходит уведомление с кнопками воронки. Если контакта нет, бот спрашивает
его обычным путём отклика. Повторные нажатия и повторный вызов приглашения ничего не дублируют.
Написать можно только тем, у кого есть чат с ботом; остальным работодатель пересылает `applyUrl`.

В карточке вакансии и приглашениях график теперь пишется по-русски («сезонная», «временная»,
«постоянная») вместо кода `seasonal`/`temporary`/`permanent`. В API значения не изменились.

### Фичи к финалу (v0.6.0)

| Что | Маршруты и поведение |
|---|---|
| **Регионы** | Справочник 85 субъектов РФ (`backend/src/regions/dictionary.ts`) распознаёт свободный текст: «под Краснодаром», «Кубань», «Питер». У вакансии сохраняется `region_subject`, в ответах — `subject { code, name }`, исходный `regionCode` не меняется. `GET /api/regions` — список для выбора. Фильтр `region_code` в каталоге принимает код субъекта или исходный текст. Старые вакансии получают код при старте backend |
| **Бенчмарк по региону** | Запрос к «Работе России» по региону (`/vacancies/region/<13 цифр>`, проверено живым вызовом). Если в регионе меньше 5 вакансий с зарплатой — по России. В ответе `scope` и `regionName` |
| **Предпросмотр в боте** | После 6 вопросов бот сохраняет черновик и показывает карточку ровно такой, какой её увидят кандидаты, с кнопками «Опубликовать» / «Оставить черновиком». Решает только автор |
| **Набор бригады** | `headcount` у вакансии («Нужно человек: N» в карточке). В каталоге — `headcount` и `spotsLeft`. Когда нанято столько же, вакансия закрывается, кандидатам на этапах «Новый» и «На связи» уходит вежливый отказ, работодатель получает сообщение. `PATCH /api/applications/:id` возвращает `vacancyClosed` |
| **QR-объявление** | `GET /api/vacancies/:id/poster.svg` — лист A4 для доски объявлений с QR. `GET /api/vacancies/:id/qr.svg` — только QR. Отклики с QR помечаются `source = qr` |
| **Источники откликов** | `applications.source`: `card`, `link`, `qr`, `subscription`, `channel`, `miniapp`, `team`. `GET /api/vacancies/:id/stats` — по источникам и этапам |
| **Подходит студентам** | `student_friendly` у вакансии, строка в карточке, фильтр `GET /api/jobs?student_friendly=true` |
| **Подписки** | `GET/POST/DELETE /api/me/subscriptions`: регион, категория, график, зарплата от, только для студентов. После публикации подходящим подписчикам приходит карточка в личный чат: одному человеку одна вакансия один раз, работодателю и уже откликнувшимся — нет. В боте: «Присылать похожие вакансии» после отклика, `/отписаться` |
| **Каналы партнёров** | Вуз или центр занятости добавляет бота в свой канал (событие MAX `bot_added`). Владелец включает публикацию, регион и «только для студентов» через `GET/PATCH /api/partner-channels`. Подходящие вакансии публикуются туда с кнопкой-ссылкой. На обычные сообщения в таких чатах бот не отвечает |
| **Выход на смену** | `PATCH /api/applications/:id/shift { start_at, note }` для приглашённых и нанятых. Кандидат сразу получает время, место и кнопки «Приду» / «Не смогу», накануне (за ~18 ч) бот напоминает тем, кто не ответил. Ответ уходит работодателю; при отказе — сколько кандидатов ещё в воронке |

### «Надёжный работодатель» (v0.7.0)

Отметку нельзя поставить себе самому или купить: её дают люди, которые реально вышли на работу.
Засчитывается найм (`hired`), если кандидат сам подтвердил выход на смену кнопкой «Приду»
(`attendance = confirmed`). Считаются разные люди, а не записи; не засчитываются сам работодатель
и пользователи без личного чата с ботом. Нужно не меньше `TRUSTED_EMPLOYER_MIN_HIRES` (по
умолчанию 5) таких людей; число вакансий не важно — у кафе может быть одна вакансия «Бариста».
Отметка считается на лету:
если найм отменить, она пропадёт сама.

Где видна: `employer.trusted` и `employer.confirmedHires` в каталоге, карточке вакансии и истории
откликов работника; строка «✓ Надёжный работодатель» в карточке вакансии в MAX (место под неё
зарезервировано в лимите 4000 символов); `employerTrust { trusted, confirmedHires, threshold }`
в `GET /api/me` — для прогресса в кабинете работодателя.

Рассылки по подпискам и в каналы запускаются в фоне после публикации и не влияют на её результат.
Время смены в сообщениях показывается по МСК.

### Валидация, дорожная карта отклика и бейджи (v0.8.0)

**Валидация.** Общие правила для REST и диалога бота (`backend/src/text.ts`, `validation.ts`):
- все тела запросов строгие — лишнее поле даёт 400 с `fields: { "имя": ["unknown field"] }`;
- однострочные поля (название, регион, категория, контакт) нормализуются: пробелы и переносы
  схлопываются; управляющие и невидимые символы отклоняются; непустое значение должно содержать
  букву или цифру;
- зарплата — до 10 000 000 ₽, id — только целое число или строка из цифр, целые в query — только
  цифры, `init_data` — до 8 КБ, смена — не дальше чем через год;
- бот применяет те же ограничения длины и потолок зарплаты (раньше ответ «40000-99999999999»
  ронял создание вакансии ошибкой БД).

**Дорожная карта отклика.** Журнал `application_events` фиксирует время каждого шага.
`GET /api/applications/:id/timeline` (кандидат или работодатель) и поле `timeline` в
`GET /api/me/applications` отдают этапы 📨 Отклик отправлен → 👀 Работодатель посмотрел →
📞 На связи → ✉️ Приглашение → ✅ Выход подтверждён → 🎉 Нанят. У каждого этапа есть `state`
(`done`, `current`, `upcoming`, `skipped`) и `reachedAt`, плюс итог: нанят, отказ или набор
закрыт. «Посмотрел» фиксируется при первом открытии списка откликов работодателем или смене
этапа. Время для подсказки по наведению (чч.мм) frontend берёт из `reachedAt`.

**Бейджи вакансии.** `GET /api/badges` — 51 бейдж в 8 группах (жильё, питание, дорога, оплата,
условия, кому подходит, график, место), например `🏠 Жильё бесплатно`, `🍲 3-разовое питание`,
`🎫 Билеты оплатят`. Вакансия принимает до 12 ключей в `badges`, в ответах приходят объекты
`{ key, emoji, label }`. Бейджи печатаются в карточке MAX и на QR-плакате, каталог фильтруется
`?badges=housing_free,meals_3`.

## Проверки и материалы для жюри

Подробные команды, ожидаемые ответы и сценарий в мобильной/веб-версии MAX приведены в
[test-data/README.md](test-data/README.md). Локальная автоматическая проверка использует
два отдельных синтетических аккаунта и подготовленную вакансию; она не отправляет сообщения
в MAX и не выдаёт моделируемую публикацию за настоящую интеграцию.

CI выполняет сборку backend, проверку Prisma и миграций PostgreSQL, `/health`, ESLint,
тесты и сборку frontend, валидацию OpenAPI. Для обоих вариантов Compose дополнительно
проверяются Nginx и REST-сценарий с синтетическими данными. CI определяет HTTP-порт из
фактической конфигурации Compose, поэтому учитывает фиксированный production-порт 80.

После развёртывания заполните `api.base_url` в `DATA-API.yaml`, добавьте публичный адрес
в `openapi.yaml`, проверьте настоящую публикацию/отклик/уведомления в MAX и зафиксируйте
commit hash сдаваемой версии. В презентации укажите ссылку на бота и служебные доступы.
Реальный адрес и секреты сейчас не заданы; `deployment_pending` в DATA-API отмечает этот статус.

## Известные ограничения

- Карточка вакансии публикуется в чат самого работодателя (для демо/пересылки кандидатам), а не
  в отдельную ленту вакансий для кандидатов — это отдельная задача за рамками текущего MVP.
  Для отклика из пересланного чата есть deep-link кнопка (см. сценарий выше).
- Регион вакансии — свободный текст от пользователя, без сопоставления со справочником кодов
  регионов trudvsem.ru; бенчмарк ищет только по названию должности, без фильтра по региону.
- Структура ответа MAX Bot API (`message_created`/`message_callback`/`bot_started`) и
  trudvsem.ru API подтверждена по документации, но не полным набором живых вызовов — помечено
  `TODO` в коде там, где это существенно.
- Напоминание работодателю о вакансии без откликов проверяется раз в час (`CHECK_INTERVAL_MS`
  в `backend/src/vacancies/reminders.ts`), а не мгновенно по истечении 48 часов — точность в пределах часа.
- Ограничение частоты запросов к trudvsem — фиксированный минимальный интервал между вызовами
  (`backend/src/trudvsem/rateLimiter.ts`), не основано на официально задокументированных лимитах —
  они нигде не опубликованы.
- Исходящие сообщения в MAX соблюдают документированный лимит 2 сообщения/сек на один чат
  (`backend/src/max/client.ts`, минимальный интервал между отправками в один `chat_id`), но
  полноценной персистентной очереди и retry с backoff при ошибке нет — при сбое каждый вызов
  просто логирует ошибку (см. try/catch на местах отправки). Для MVP-нагрузки хакатона это
  осознанно принятый риск, а не забытая задача.
- Вебхук отвечает `200` даже если внутренняя обработка апдейта упала (ошибка только логируется) —
  это защищает от retry-шторма при НАШИХ сбоях, но полноценной дедупликации повторных апдейтов
  MAX по их id нет: теоретический повторный апдейт может продвинуть диалог на лишний шаг
  (см. TODO в `backend/src/max/webhook.ts`).
- Предпросмотр и явное подтверждение вакансии перед публикацией не реализованы — бот публикует
  карточку сразу по завершении диалога из 6 шагов (раздел 3.8 хендоффа фронтенда, отдельное
  расширение сценария за рамками текущего MVP).
- Кабинет работника проверен интеграционными тестами с моком MAX, но не живым сценарием на двух
  аккаунтах MAX (публикация → каталог → отклик → статус → история, пересылка карточки → текстовая
  ссылка → контакт). Точный рендер markdown-ссылки в пересланном сообщении не подтверждён вживую.
- Кандидат, который откликнулся из мини-приложения и ни разу не запускал бота лично
  (`hasBotChat=false`), не получит уведомлений о статусе: писать первым пользователю, не начинавшему
  диалог, документация MAX не подтверждает. Отклик при этом сохраняется, статус виден в
  `GET /api/me/applications`. Пользователи, писавшие боту до этой версии, получат `hasBotChat=true`
  только после следующего `bot_started` (например, перехода по ссылке отклика).
- Справочника категорий нет — `GET /api/jobs/filters` отдаёт исходные значения категорий.
  Регион распознаётся по основам слов; нераспознанный текст остаётся как есть (`subject = null`).
- Рассылки по подпискам и в каналы — без очереди с повторами: сбой отправки одному получателю
  логируется, повторно ему эта вакансия не придёт. Не больше 500 получателей на вакансию.
- Время выхода на смену в сообщениях — по МСК; часовые пояса регионов не учитываются.
- «Надёжный работодатель» учитывает только наймы с подтверждённым выходом (S4): наймы до
  появления подтверждения смены и без назначенной смены не засчитываются. Уже отправленные
  карточки в MAX не обновляются, отметка появится в следующих.
- Шаг «Сколько человек нужно» и отметка «для студентов» задаются только в мини-приложении,
  диалог бота их не спрашивает (чтобы не удлинять 6 вопросов).
- Живой проверки в MAX требуют: кнопки предпросмотра, приглашения на смену, `bot_added` в
  реальном канале и публикация в канал от имени бота (бот должен быть администратором канала).
- Проверки frontend и REST API на синтетических данных не заменяют живую проверку
  публикации и уведомлений в MAX. До развёртывания эта часть остаётся непроверенной.
